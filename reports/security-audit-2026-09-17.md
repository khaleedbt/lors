# Проверка безопасности LORS — 17.09.2026

Проверены исходники Django/DRF, API, сериализаторы, загрузка файлов, AI-ассистент, настройки, конфигурация nginx/systemd и закреплённые зависимости. Рабочий сервер, реальные настройки nginx/TLS и доступность репозитория извне не проверялись. Код не изменён. Локальные воспроизведения не записывали данные в БД и не вызывали платные API.

## 1. Высокий риск: дампы с чувствительными данными хранятся в Git

`git ls-files` подтверждает, что `lors.sql` и `lors.dump` отслеживаются. В SQL обнаружены:

- `lors.sql:701`: одна запись auth_user с хешем пароля;
- `lors.sql:793`: три записи django_session;
- `lors.sql:1977`: две жалобы с именами, телефонами и текстом.

Любой получивший репозиторий получает эти данные и возможность подбирать пароль офлайн. Сессии опасны, если ещё действуют; их актуальность не установлена. Это подтверждённое наличие данных в Git, а не доказательство публичной утечки.

Исправление: исключить дампы из репозитория и добавить правила игнорирования. Если данные реальные и репозиторий передавался посторонним — сменить соответствующие пароли и отозвать сессии. Удаление только из текущего коммита сохраняет данные в истории; очистку истории согласовать с командой отдельно.

## 2. Высокий риск: обход ограничения запросов через X-Forwarded-For

`deploy/nginx_lorssy.com.conf:19` использует `$proxy_add_x_forwarded_for`: nginx сохраняет присланный клиентом префикс и добавляет фактический адрес. В REST_FRAMEWORK отсутствует NUM_PROXIES, поэтому установленный DRF использует всю строку X-Forwarded-For как идентификатор. В `lors/meta_capi.py:95` выбирается первый, контролируемый клиентом элемент.

Локальное воспроизведение с одним реальным IP: шесть попыток для lead_create с одинаковым заголовком дали `[True, True, True, True, True, False]`; шесть попыток с разными подставными префиксами дали шесть True. OriginAllowed не устраняет проблему: скрипт может передать разрешённый Origin.

Последствия: спам заявок и отзывов, расход диска при загрузке фотографий, обход ограничений каталога и Meta API.

Исправление: на доверенном входном nginx перезаписывать заголовок фактическим адресом; настроить NUM_PROXIES согласно реальной цепочке прокси и единый безопасный способ получения IP для Meta. Для показанной схемы с одним nginx подходит NUM_PROXIES=1. Использовать общий кэш для воркеров и ограничения nginx. Нельзя выбирать число прокси без проверки реальной схемы размещения.

Документация: https://www.django-rest-framework.org/api-guide/throttling/#how-clients-are-identified

## 3. Средний риск: неограниченный рост памяти и потоков на Meta endpoint

`lors/meta_capi.py:50–63`: словарь `_rate_buckets` сохраняет каждый новый идентификатор навсегда. Старые элементы очереди чистятся только при повторном обращении к тому же идентификатору, сами ключи не удаляются. Локальная проверка 500 произвольных идентификаторов оставила 500 ключей.

`lors/meta_capi.py:222`: каждое принятое событие создаёт новый поток без общего ограничения параллелизма. При настроенном Meta API потоки выполняют сетевые запросы с таймаутами и повторами. В сочетании с обходом лимитов это позволяет расходовать память и ресурсы процесса.

Исправление: хранить ограничения в общем кэше с TTL; отправлять события через очередь с ограниченным числом работников, ограничить размер очереди и общий входящий поток.

## 4. Средний риск: подделка событий покупки для Meta

`lors/meta_capi.py:200–222` принимает Purchase и произвольный customData от публичного клиента без связи с подтверждённым заказом или оплатой. Локально событие Purchase с вымышленной суммой прошло до создания отправителя; реальная отправка была заменена mock.

При включённом Meta API злоумышленник может загрязнять аналитику конверсий. Проверка Origin не удостоверяет клиента. Это не подмена фактической оплаты в базе проекта.

Исправление: генерировать Purchase на сервере после подтверждённого бизнес-события; брать сумму и валюту из заказа, проверять уникальность события. Для остальных событий ввести сериализатор с проверкой типов и длины полей.

## 5. Средний риск: фотографии заявок раздаются без авторизации

`lors/models.py:302` сохраняет фотографии заявок в `media/leads/`. `deploy/nginx_lorssy.com.conf:11` раздаёт всю media напрямую. IsAdminUser защищает просмотр заявки через API, но не доступ к самому файлу по известному URL.

Пользователь, получивший ссылку, может прочитать фото без staff-сессии. Угадываемость конкретных имён и размещение реальных приватных документов не проверялись; перечисление каталога конфигурацией не включено.

Исправление: хранить фотографии заявок в закрытом хранилище, выдавать после проверки прав через X-Accel-Redirect или временные подписанные ссылки. Публичные изображения товаров и опубликованных отзывов обслуживать отдельно.

## Дополнительные риски конфигурации и раскрытия данных

- `config/settings.py:27`: известный резервный SECRET_KEY. Риск возникает при отсутствии реального ключа в окружении. Убрать резервное значение, завершать запуск при отсутствии ключа.
- `config/settings.py:30`: DEBUG включён по умолчанию. При пропущенной переменной это раскрывает технические подробности ошибок. Безопасное значение по умолчанию — False.
- `lors/serializers.py:58`: публичный каталог содержит template_code, notes и sheet_row. В системном промпте ассистента template_code явно назван служебной информацией. Если эти поля действительно внутренние, убрать их из публичного сериализатора; инструкция модели не защищает публичный API.
- Проверка Django с явным DEBUG=False сообщила security.W004: HSTS отключён. Включать после проверки HTTPS и требуемых доменов.
- Показанный nginx слушает только HTTP. TLS может настраиваться в другой конфигурации; фактическую защиту рабочего сервера по этому файлу установить нельзя.

`DEBUG=False python manage.py check --deploy`: security.W004 и четыре предупреждения генерации OpenAPI; последних не следует считать подтверждёнными уязвимостями. Первый запуск без переопределения DEBUG остановился из-за унаследованного значения `release`; источник этого значения не установлен.

Не обнаружены очевидные вызовы eval/exec, небезопасная десериализация или ручная конкатенация SQL в рассмотренном прикладном коде. Это не исключает другие ошибки. Общий набор тестов не запускался; сделаны целевые проверки без доступа к БД.

Приоритет исправлений: дампы и возможные скомпрометированные учётные данные → доверенные IP и ограничения запросов → приватное хранение фото → очередь Meta и проверка событий → безопасные настройки по умолчанию.

## Исправления в рабочем дереве

Добавлены безопасные значения настроек, обязательная проверка SECRET_KEY, доверенная обработка IP, общий файловый кэш, ограничение запросов nginx, ограниченная очередь отправки Meta, валидация событий и запрет публичного Purchase. Фотографии заявок обслуживаются Django только для staff; nginx должен проксировать этот путь. Из публичного ответа каталога убраны внутренние поля. Добавлены ограничение длины сообщения ассистента и сравнение сервисного ключа через compare_digest. Дампы сняты с отслеживания с сохранением локальных копий.

Семь целевых тестов прошли без обращения к БД. Проверка deploy оставляет прежние предупреждения OpenAPI-аутентификации и отключённого HSTS. nginx отсутствует в локальном окружении, поэтому nginx -t необходимо выполнить на сервере. Изменения пока не развёрнуты; прежняя конфигурация сервера продолжит публично раздавать фото до применения новых правил. История Git, действующие пароли и сессии не изменялись.
